# Deploying Lightseed Studio on Railway

Railway hosts only the edge: TLS, the domain, Google sign-in and a reverse
proxy. Every job, model, image and byte of storage stays on the owner's PC. If
the PC is off, visitors get a branded "Lightseed Studio is offline" page.

```
Browser --HTTPS--> Railway service (deploy/railway)
                     oauth2-proxy   :$PORT          Google sign-in
                       -> gateway  127.0.0.1:18080  injects identity + token
                         -> tailscaled userspace   127.0.0.1:1055
                   --Tailscale--> PC 100.98.64.62:8766
```

The container is built from `deploy/railway` and runs `tailscaled`,
`oauth2-proxy` and a zero-dependency Node gateway. Nothing here is
typeable-from-memory: every value below is either generated by you or copied
from a dashboard. Do the four setups in order; the service does not start
correctly until all four are done.

---

## 1. Google sign-in (OAuth client)

You need a Google Cloud project you control. The sign-in is email-only: the app
requests `openid email` and nothing else (no profile, no Drive, no gmail).

1. <https://console.cloud.google.com/> -> create or pick a project.
2. **APIs & Services -> OAuth consent screen**
   - User type: **External**.
   - App name `Lightseed Studio`; support email = yours; developer contact =
     yours.
   - Scopes: only `.../auth/userinfo.email` and `.../auth/openid`.
   - **Publishing status: Testing** while you have a handful of users.
3. **APIs & Services -> Credentials -> Create credentials -> OAuth client ID**
   - Application type: **Web application**.
   - Name: `lightseed-railway`.
   - **Authorised redirect URI** — exactly this, once you know the domain:
     `https://<your-service>.up.railway.app/oauth2/callback`
   - Leave "Authorised JavaScript origins" empty.
4. Copy the **Client ID** and **Client secret**; they become
   `OAUTH2_PROXY_CLIENT_ID` and `OAUTH2_PROXY_CLIENT_SECRET`.

### Testing mode is a second allowlist — with a 7-day catch

While the consent screen stays in **Testing**, only addresses listed under
**Test users** can complete sign-in (Google refuses everyone else before the
request ever reaches Railway). That is convenient: it is a second gate in front
of the PC's own invitation list.

The catch: refresh tokens issued in Testing mode expire after **7 days**, so
every test user has to sign in again roughly weekly. For a small group of
invited people that is usually acceptable. To remove it, publish the app
(**Publish app**), which drops the 7-day limit but also removes the Test-user
gate — at which point the PC's invitation list is the only allowlist, which is
the state the design expects anyway. Publishing requires Google verification
only if you request sensitive scopes; `openid email` is not sensitive, so an
unverified published app showing "unverified app" is normally fine for a
private tool.

Changing the redirect URI later (a new domain) means editing the OAuth client —
an unmatched URI fails at the callback with `redirect_uri_mismatch`, before any
Lightseed code runs.

## 2. Tailscale (tag, ACL, ephemeral key)

The container joins your tailnet as an **ephemeral** node tagged
`tag:railway`, and the ACL lets that tag reach **only** the PC's remote port.

### 2.1 Tag

Tailscale admin console -> **Access controls**. Add the tag owner and define
the tag:

```jsonc
{
  "tagOwners": {
    "tag:railway": ["autogroup:admin"]
  },
  "acls": [
    // The edge may open connections to the PC's remote port, and nothing else.
    {
      "action": "accept",
      "src": ["tag:railway"],
      "dst": ["100.98.64.62:8766"]
    }
  ]
}
```

Notes:

- `100.98.64.62` is this PC's Tailscale address; keep it in the ACL. If the PC's
  address ever changes, update **both** the ACL and `LIGHTSEED_UPSTREAM`.
- The rule is one-way and port-specific: the Railway node cannot reach the PC's
  SSH, the local UI on 8765, any other tailnet device, or the internet through
  the tailnet.
- Ephemeral nodes get their tag from the auth key, so the ACL above is the whole
  story — no separate device approval step.

### 2.2 Ephemeral, reusable auth key

Admin console -> **Settings -> Keys -> Generate auth key**:

- **Ephemeral**: on. The node disappears from the machine list when the
  container stops, so restarts cannot pile up devices.
- **Reusable**: on. Every container boot re-registers.
- **Expiry**: 90 days. Put a calendar reminder to rotate it; when it expires the
  service stops booting with a clear `tailscale up failed` message.
- **Tags**: select `tag:railway`.
- **Devices**: optionally pre-approve if your tailnet requires device approval.

Copy the key (`tskey-auth-...`). It becomes `TS_AUTHKEY`. Treat it as a
credential: anyone with it can join your tailnet as `tag:railway` until it
expires.

The container runs:

```bash
tailscaled --tun=userspace-networking --state=mem: \
           --outbound-http-proxy-listen=127.0.0.1:1055 -port=0
tailscale up --authkey=$TS_AUTHKEY --hostname=lightseed-railway --reset
```

`--state=mem:` plus the ephemeral key is what makes the node disposable; there
is no state volume, no TUN device and no privileged mode.

### 2.3 The PC's side

`./start-web.sh` turns on the remote listener when two things are present:

1. **The token file**, `cache/remote-token`, holding the same text as
   `LIGHTSEED_PROXY_TOKEN`, readable only by you:

   ```bash
   (umask 077; openssl rand -base64 32 > cache/remote-token)
   cat cache/remote-token    # paste this value into LIGHTSEED_PROXY_TOKEN
   ```

2. **The public origin**, exported before starting the server:

   ```bash
   QWEN_REMOTE_ORIGIN=https://<your-service>.up.railway.app ./start-web.sh
   ```

The launcher then adds `--remote-port 8766 --remote-host <tailscale ip -4>
--remote-token-file cache/remote-token --remote-origin $QWEN_REMOTE_ORIGIN`.
Startup prints `qwen-web remote listener on http://100.x.y.z:8766` when it is
on. Invite people on the **Admin** tab of the local page (port 8765); everyone
starts with Q8 only.

## 3. Secrets you generate

Run these locally; never paste them into a repository or a chat.

```bash
# The shared secret the gateway sends to the PC: use the value already in the
# PC's cache/remote-token (section 2.3), not a second one.
cat cache/remote-token           # -> LIGHTSEED_PROXY_TOKEN
# oauth2-proxy cookie secret: any of 16, 24 or 32 bytes, base64 encoded.
openssl rand -base64 32          # -> OAUTH2_PROXY_COOKIE_SECRET
```

`LIGHTSEED_PROXY_TOKEN` must be at least 32 characters (the entrypoint refuses
shorter ones). The cookie secret must decode to exactly 16, 24 or 32 bytes; the
entrypoint checks this at boot rather than letting oauth2-proxy fail later.

## 4. Railway variables

Create the service, open **Variables**, and add every row. `PORT` is injected by
Railway — do not set it.

| Variable | Value | Notes |
|---|---|---|
| `LIGHTSEED_PUBLIC_URL` | `https://<service>.up.railway.app` | No trailing slash; must be `https`. Used for the OAuth redirect and cookie domain. |
| `LIGHTSEED_UPSTREAM` | `100.98.64.62:8766` | `host:port` of the PC's remote listener. No scheme. |
| `LIGHTSEED_PROXY_TOKEN` | `openssl rand -base64 32` | Must match the PC's `remote-token` file. |
| `TS_AUTHKEY` | `tskey-auth-...` | Ephemeral, reusable, `tag:railway`. |
| `OAUTH2_PROXY_CLIENT_ID` | from Google | |
| `OAUTH2_PROXY_CLIENT_SECRET` | from Google | |
| `OAUTH2_PROXY_COOKIE_SECRET` | `openssl rand -base64 32` | 16/24/32 decoded bytes. |
| `LIGHTSEED_HOSTNAME` | `lightseed-railway` *(optional)* | Tailscale machine name. |
| `LIGHTSEED_VERSION` | short git sha *(optional)* | Shown on the offline page. Defaults to `unknown`. |
| `LIGHTSEED_LOG_REQUESTS` | `1` *(optional)* | One line per proxied request, identity hashed to 12 hex chars. |
| `LIGHTSEED_CONNECT_TIMEOUT_MS` | `10000` *(optional)* | How long to wait for the TCP connection to the PC. It does **not** cap thinking time: once connected, a request may run up to `LIGHTSEED_UPSTREAM_IDLE_TIMEOUT_MS` (330 s) as long as bytes keep moving. Raise it only if a cold Tailscale path is genuinely slower. |

Rate limits have defaults (30 requests / 10 s per email; 5 job submissions /
60 s) and can be tuned with `LIGHTSEED_RATE_LIMIT_MAX` and
`LIGHTSEED_JOB_RATE_LIMIT_MAX`. Tune them only with a reason: they exist to keep
one invited person from monopolising the PC's single GPU queue.

Never commit any of these. `railway.toml` deliberately contains no secrets.

## 5. Deploying on the free plan

1. Push the `railway` branch to GitHub (this repo).
2. <https://railway.app/new> -> **Deploy from GitHub repo** -> pick the repo.
3. Service -> **Settings -> Source**:
   - Branch: `railway`
   - **Root Directory: `deploy/railway`** (required — the image is built from
     that directory only)
4. Service -> **Settings -> Deploy**, and set these by hand:
   - **Healthcheck Path**: `/healthz`
   - **Healthcheck Timeout**: `30`
   - Restart policy: **On failure**, max retries `10`

   `deploy/railway/railway.toml` records the same values, but it is **not
   applied**: Railway deprecated Config as Code, new services cannot opt into
   it, and `railway.json` / `railway.toml` stop being read on **2026-12-01**
   (see <https://docs.railway.com/config-as-code>). Treat the file as
   documentation of the intended settings; the dashboard is what takes effect.
5. **Settings -> Networking -> Generate Domain**. Copy it into
   `LIGHTSEED_PUBLIC_URL`, and add
   `https://<domain>/oauth2/callback` as the Google redirect URI (step 1.3).
6. Add all variables from step 4, then **Deploy**.

Health and restarts: Railway polls `GET /healthz`.

- `200 {"status":"ok"}` — Tailscale is up and the PC answers.
- `200 {"status":"degraded"}` — Tailscale is up, the PC is off. Deliberately
  **200**: a switched-off PC must not make Railway restart the service in a
  loop.
- `503 {"status":"tailscale_down"}` — the node is not on the tailnet; that is a
  real container fault, so Railway restarts it (`ON_FAILURE`, up to 10 times).

The health body never contains an address, only `tailscale`, `upstream` and
`version`.

Free-plan realities worth knowing before you invite anyone:

- The service sleeps after inactivity on the free plan. The first visitor after
  a sleep pays a cold start (container boot + `tailscale up`, typically 10-30 s)
  and may see the offline page once; a refresh works.
- Egress and build minutes are capped. Idle proxying is cheap; generated images
  are small, but a long session of large downloads counts.
- Railway's edge has its own idle timeout. The proxy allows 330 s upstream, but
  if Railway closes an idle connection before a long generation finishes, the
  browser sees a network error rather than a Lightseed error. Progress requests
  from the UI keep the connection warm; a single request idle for many minutes
  is the risky case.
- Do not add replicas. The proxy token, the Tailscale node identity and the
  in-memory rate limiter are all per-container.

First-run verification:

```bash
curl -sS https://<domain>/healthz
# {"schema":"lightseed.gateway_health.v1","status":"ok","tailscale":"running",
#  "upstream":"reachable","version":"<sha>"}
curl -sS -o /dev/null -w '%{http_code}\n' https://<domain>/
# 403 -- the sign-in page. oauth2-proxy 7 answers an unauthenticated browser
# with the page (status 403), not a redirect; the button then goes to Google.
# Do not follow redirects when checking /oauth2/start: the 302 points at
# accounts.google.com, and following it reports Google's 200 as a pass.
curl -sS -o /dev/null -w '%{http_code} %{redirect_url}\n' \
  "https://<domain>/oauth2/start?rd=/"
# 302 https://accounts.google.com/o/oauth2/auth?... -- the real redirect
```

Then open the domain in a browser, sign in with an invited Google account, and
check that the PC's invitation list is what actually decides access.

## 6. Rotating secrets and keys

| Secret | How to rotate | What breaks if you skip the other side |
|---|---|---|
| `LIGHTSEED_PROXY_TOKEN` | Generate a new value; update the PC's `remote-token` file and restart the PC's server; update the Railway variable. Do the PC first, then Railway, so there is never a window where the edge sends a token the PC rejects. | PC answers 401 to every proxied request. |
| `OAUTH2_PROXY_COOKIE_SECRET` | Generate a new base64 secret; update the variable; Railway restarts. | Every existing session is invalidated — visitors sign in once more. That is the point. |
| `OAUTH2_PROXY_CLIENT_SECRET` | Google Console -> the client -> **Reset secret**; update the variable immediately. | Sign-in fails with `invalid_client` until the values match. |
| `TS_AUTHKEY` | Generate a new ephemeral key, update the variable, redeploy; revoke the old key in the Keys list. | The node cannot re-register; `/healthz` reports `tailscale_down` and Railway restart-loops on failure. |
| Tailscale node | If the container is compromised: admin console -> Machines -> delete `lightseed-railway`; rotate the auth key and both edge secrets. | — |

Rotation checklist, in order, for the token: PC file -> PC restart -> Railway
variable -> confirm `/healthz` still says `ok` -> sign in and generate one
image.

## 7. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Boot fails `TS_AUTHKEY is required` | Variable missing | Add it (step 4). |
| Boot fails `tailscale up failed` | Key expired, revoked, or a different tag | New key with `tag:railway`. |
| `/healthz` says `tailscale_down` | Node not Running | Check the key expiry and the machine list. |
| `/healthz` says `degraded`, page offline | PC off, server not running, or the ACL blocks the port | Start the PC's server; confirm the ACL destination and `LIGHTSEED_UPSTREAM`. |
| Offline page after about 10 s on a job the PC is still working on | Not the PC: `LIGHTSEED_CONNECT_TIMEOUT_MS` expired. With the shipped build this cannot happen once the connection is up — it applies to reaching the PC, not to waiting for an answer. If you see it, the connection never established. | Check the tailnet path and the ACL, not the job. |
| `gateway did not listen on ... within 30s` at boot | The gateway exited, or the port in the message is wrong for the mode | Read the gateway's own log line above it; it names the address it bound. |
| `/healthz` still says `ok` a few seconds after the PC is stopped | The snapshot is cached for 5 s (`LIGHTSEED_HEALTH_CACHE_MS`) | Wait, then re-probe. This is deliberate; it stops a probe burst from hammering the PC. |
| `redirect_uri_mismatch` at Google | Redirect URI not exactly `https://<domain>/oauth2/callback` | Fix the OAuth client. |
| Sign-in succeeds, pages 401 | Proxy token mismatch | Rotate as in step 6. |
| Offline page while the PC is up | `LIGHTSEED_UPSTREAM` address wrong, or the PC's remote listener is not enabled | Check the PC's `--remote-port` and Tailscale address. |
| `403` after sign-in, "not invited" | Google account is not on the PC's invitation list | Add it from the PC's admin route. |

## 8. Local verification

No Railway, Google or Tailscale account is needed for these:

```bash
cd deploy/railway
node --test test/     # gateway: header rewriting, streaming, offline page,
                      # rate limits, health, bad targets -- loopback only
./smoke.sh            # builds the image and runs it twice: dev mode against a
                      # fake PC, then the real sign-in chain
```

`oauth2-proxy`'s flags live in `deploy/railway/oauth2-proxy.args`, one argument
per line, verbatim (no word splitting, no globbing). The smoke test feeds the
same file to the same binary, so the flags that ship are the flags that were
exercised. Secrets are the exception: they come from `OAUTH2_PROXY_*`
environment variables and never touch the image or the process list.

`./smoke.sh` uses ports 8770-8777 and needs docker or podman. Dev mode is the
only mode where sign-in is skipped, and `entrypoint.sh` refuses dev mode if
OAuth credentials are present, so it cannot mask a production misconfiguration.

The second half of the run is the production chain: the real `entrypoint.sh`
starts the real `oauth2-proxy` from the shipped arguments file with the gateway
behind it, and `tailscaled`/`tailscale` are replaced by the shims in
`test/fake-tailscale` (mounted read-only, never copied into the image). That
proves the sign-in boundary without a Google account, a tailnet or a secret.

The smoke run asserts: client `X-Lightseed-*` headers stripped, identity
injected and lowercased, `X-Qwen-UI`/`Origin` passed through, a chunked response
delivered while the upstream is still open, a 3 s reply not cut short, a 12 s
reply (longer than the connect timeout) served instead of being replaced by the
offline page, the branded 503 page when the PC disappears, a real upstream
`qwen_engine.web_error.v1` 502 passed through while a blank one is replaced,
`/healthz` in both states, and a clean `SIGTERM` shutdown.

The production-chain block additionally asserts: an anonymous browser gets the
branded 403 page with the Google button, the privacy notice and the inlined
logo; `/oauth2/start` redirects to `accounts.google.com` with `openid email`
only and the public `/oauth2/callback`; a client-supplied `X-Forwarded-Email`
does not authenticate; the gateway answers `/healthz` through the proxy; and
`oauth2-proxy` accepted the shipped arguments (a rejected flag fails the run).

# v100-qwen-image

A hand-rolled [Qwen-Image-2.1](https://huggingface.co/Qwen/Qwen-Image-2.1)
text-to-image engine built to run on a single **Tesla V100** (Volta, sm_70),
16GB or 32GB. It provides a headless CLI and a local web workspace, sharing one
engine. Image quality comes first; speed is improved where it does not cost
quality.

The design follows an earlier LTX-2.5 ROCm build: a CPU-only engine core with
heavy ML imports deferred to adapters, a separate encoder subprocess, an
embedding cache, pinned model assets and measured VRAM calibration.

## Status

Working today on a real V100:

- **Text-to-image** at FP16 (default) or **Q8_0 GGUF** (experimental).
- **All seven upstream aspect ratios** at 1K and 2K (`--preset`), e.g. 1024²,
  2048², 2752×1536 landscape, 1536×2752 portrait.
- **Web workspace** with prompt-first layout, live progress, cancellation,
  session history, config import/export, three themes and in-UI help for every
  option.
- **Turbo recipe** (`--recipe turbo`, or Quality/Turbo in the web workspace):
  the official 8-step Turbo transformer with the base encoder and VAE. Sampling
  is ~5x faster; total run time barely moves because loading dominates.
- **Transparent backgrounds** (`--transparent`, or the web checkbox): a
  see-through background saved with a real alpha channel in PNG or WebP.
- **Reference-image editing** (up to 10 ordered images, web or
  `--reference`): **experimental** — works end to end, and edits are
  reproducible: an edit's noise is derived from the seed **and** the ordered
  references, so the same seed with the same references reproduces the image. A
  1024×1024 seed-42 edit is clean in base FP16 and Turbo; the old
  over-processed look was noise reuse (references generated by this engine at
  that size and seed), fixed in `ab2f3ab`. FP16 edits keep the KV cache off and
  decode in FP32; edits above ~1088×1024 need tiled decode, and 1152² and up do
  not fit in FP16 on a 16 GB card.
- **Optional prompt rewriting** through a local OpenAI-compatible service,
  off by default and never applied without an explicit **Apply**.
- Output as JPG (default), PNG or lossless WebP, named
  `qi21-DDMMYYYY-<seed>` and never overwriting existing files.

Day-to-day usage, plain-language trade-offs and what is measured versus still
unknown: **[`docs/user-guide.md`](docs/user-guide.md)**.

Measured on the development machine (single runs, not a benchmark suite):

| Job | Denoise | Wall time |
|---|---|---|
| 1024², 40 steps, FP16 (Quality) | 42.0 s | ~107–109 s, measured before the hashing/encoder speed-ups |
| 1024², 8 steps, FP16 (Turbo) | 8.5 s | 68.9 s cold, 26.8 s with the prompt cached |
| 1024², 40 steps, FP16, 1 reference image | 95.4 s | 130.2 s |
| 2048², 20 steps, FP16, tiled decode | 149.5 s | ~3 m 39 s (15,835 MiB peak) |

Model loading and the CPU text encoder, not sampling, dominate a cold run —
which is why the denoise column and the wall-time column tell different
stories, and why Turbo barely shortens a cold job. Model files are now hashed
once per job and the encoder uses all cores, so cold figures measured before
that are pessimistic; [`docs/user-guide.md`](docs/user-guide.md) has the
per-stage numbers.

Not done yet: memory preflight before generation (submitting a job is **not**
a guarantee it fits) and 2K VAE-decode headroom. The 1024×1024 edit artifact is
fixed — it was noise reuse (edits now derive their sampler seed from the seed
and the ordered references, recorded as `noise_seed`), see
[`docs/user-guide.md`](docs/user-guide.md). See
[`docs/next-features-plan-2026-10-25.md`](docs/next-features-plan-2026-10-25.md)
and [`PLAN.md`](PLAN.md).

## Requirements

- Linux x86_64, Python 3.11 or 3.13, [uv](https://docs.astral.sh/uv/).
- NVIDIA Tesla V100, 16GB or 32GB, driver supporting CUDA 12.6. All
  measurements were made on the 16GB card; the 32GB card is accepted but has
  not yet been run (see [Running on another machine](#running-on-another-machine)).
- About 33 GB of disk for the base model (+ the Q8 GGUF if wanted), and enough
  host RAM for the ~17.5 GB text encoder, which runs on CPU in a child process.

torch is pinned to `2.14.1+cu126`, the last series shipping sm_70 kernels;
diffusers and transformers are pinned to exact git commits. Rationale and the
full pin table are in [`docs/dependencies.md`](docs/dependencies.md).

## Setup

```bash
# 1. Environment (hash-checked lockfile; the index flag is required)
uv venv --python 3.13 .venv
uv pip sync --python .venv/bin/python --index-strategy unsafe-best-match requirements.lock

# 2. Model weights: 24 files pinned by revision and SHA256 in models/manifest.json.
#    Generation never downloads on its own; you either press Download in the
#    page (loopback only) or run the explicit fetch below.
.venv/bin/python tools/fetch_models.py --manifest models/manifest.json \
    --models-dir models/assets --fetch
```

Open the page after `./start-web.sh` and the **Settings → Models** section lists
every asset with its size, reason and destination, ticks the optional ones you
ask for, and downloads them on this machine — resumable, verified against the
pinned SHA256, cancellable, and refused up front if the disk cannot hold it.

Starting the server before any of that is the intended first run: an empty
`models/` starts `--enable-generation` normally (it only refuses a *job* until the
base files arrive), so the page is always reachable on a machine that has nothing
yet.
Generate stays disabled with "Models not downloaded" until the required base
assets are in place. A browser on a Tailscale or LAN address sees the command
above instead of a button, because the download belongs on the machine the
models live on. Details:
[`docs/user-guide.md`](docs/user-guide.md#first-run-getting-the-models).

The optional Q8 transformer comes from `unsloth/Qwen-Image-2.1-GGUF`
(`q8/qwen-image-2.1-Q8_0.gguf`), pinned in `models/q8_manifest.json`. It is
offered in that same list, or place it under `models/q8/` yourself.

## Usage

### Web workspace

```bash
./start-web.sh
```

Serves on port 8765 with a single shared job queue. It binds `127.0.0.1` plus
this machine's LAN and Tailscale IPv4 addresses when it has them; override
these with `QWEN_LAN_HOST`, `QWEN_TAILSCALE_HOST` and `QWEN_WEB_PORT`. It also answers to this PC's
hostname, `<hostname>.local` and its Tailscale MagicDNS name, listed in
`cache/web-settings.json` (written on first run; edit it to change them). Set `QWEN_ATTEST_UNBOUNDED_HOST=0`
when running under a cgroup memory limit. See
[`docs/lan-tailscale.md`](docs/lan-tailscale.md).

### CLI

```bash
# Show the resolved plan without loading anything
python cli_gen.py --dry-run --prompt "a lighthouse at dusk" --preset square

# Generate (an actual run needs the manifest, models, output and cache paths)
python cli_gen.py --run --prompt "a lighthouse at dusk" --preset landscape2k \
    --steps 40 --seed 42 --output-format png \
    --manifest models/manifest.json --models-dir models/assets \
    --cache-dir cache --output-dir output/runs
```

Useful options: `--quant {fp16,q8}`, `--negative` with `--true-cfg-scale`,
`--width/--height` (overrides the preset), `--[no-]tiled-decode` (2K presets
turn it on; the web API refuses an untiled 2K job, the CLI does not),
`--config FILE` (JSON `GenerationConfig`), `--transparent`, `--recipe
{base,turbo}`, `--reference PATH` (repeatable). Run `python cli_gen.py --help`
for the full list.

### Turbo recipe

`--recipe turbo` (or the web workspace's **Turbo** choice) runs the official
8-step Turbo image model instead of the reference model. It shares the
**base** text encoder, VAE and processor — only the transformer differs — so
the honest label is "Turbo transformer + base encoder/VAE".

Measured on a V100 at 1K/FP16: denoise 8.5 s vs 42.0 s for the reference
model, but a whole job 68.9 s vs 73.9 s (different cache states — see the
table above), because model loading and the text encoder dominate a run.
Turbo's saved sigmas make the step count inert, so the CLI and UI both fix
steps at 8 and **refuse** anything else rather than accepting a number that
would be ignored. Turbo is evaluated at CFG 1.0 with no negative prompt and
has no reviewed Q8 artifact: a true-CFG request (negative prompt *and* scale
above 1) and `--quant q8` are refused with a typed field error. The web
workspace locks steps, guidance, the negative prompt and quantization while
Turbo is selected, says why, and restores your own values when you switch back
to **Quality**; an imported config without a `recipe` key imports as `base`.
See [`docs/turbo-plan.md`](docs/turbo-plan.md).

### Transparent backgrounds

`--transparent` (or the web workspace checkbox) asks the model for a
see-through background and keeps the alpha channel in the saved file. JPEG
cannot store alpha, so the format must be `png` or `webp`: the CLI selects
`png` when no format was given explicitly and **refuses** an explicit `jpg`
rather than silently changing it; the UI switches `jpg` to `png` and says so.
Your prompt text is never modified — a fixed instruction is added only to the
text the model reads (`GenerationConfig.effective_prompt`). The result is
model-dependent, not a guaranteed cutout. See
[`docs/transparency.md`](docs/transparency.md).

## Running on another machine

A checklist for setting the app up on a fresh Linux machine with a V100. It is
written so that you, or an AI assistant you point at this section, can follow
it step by step. Every setting is an environment variable read by
`start-web.sh`; nothing in the repository needs editing.

### 1. Check the machine

| Need | How to check | Notes |
|---|---|---|
| Linux x86_64 | `uname -m` → `x86_64` | |
| Tesla V100, 16GB or 32GB | `nvidia-smi --query-gpu=name,memory.total --format=csv` | sm_70. Other GPUs are refused. |
| Driver for CUDA 12.6 | `nvidia-smi` shows "CUDA Version: 12.6" or higher | Tested on driver 580.178.04. |
| Host RAM ≥ 32 GB | `free -g` | The ~17.5 GB text encoder runs on the CPU in a child process. |
| Disk ≥ 45 GB free | `df -h .` | ~33 GB base model, ~9 GB optional Q8 transformer, ~19 GB optional enhancers. |
| `git`, `curl`, [uv](https://docs.astral.sh/uv/) | `uv --version` | uv installs Python 3.13 itself. |

### 2. Install

```bash
git clone https://github.com/EuanWebster/v100-qwen-image.git
cd v100-qwen-image
uv venv --python 3.13 .venv
uv pip sync --python .venv/bin/python --index-strategy unsafe-best-match requirements.lock
```

Confirm the card is recognised (prints the name, total memory and whether a
CUDA kernel ran):

```bash
PYTHONPATH=src .venv/bin/python -c "from qwen_engine.hardware_probe import probe_v100 as p; r=p(); print(r.device_name, r.resources.gpu_total_bytes, r.resources.cuda_kernel_verified)"
```

### 3. Optional: the official prompt enhancers (llama.cpp)

The Rewrite button can use Qwen's official prompt enhancers, which run under
your own `llama-server` for the length of one rewrite. Skip this section and
everything else still works.

- Build: upstream llama.cpp with CUDA for sm_70, for example
  `cmake -B build -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=70 && cmake --build build -j --target llama-server`.
  Tested at llama.cpp commit `74b104c` (2026-10-26) built with CUDA 12.4. The
  edit enhancer needs multimodal (`mtmd`) support, which the standard
  `llama-server` build includes.
- Point the launcher at it: `export QWEN_PE_LLAMA_SERVER=/path/to/llama-server`.
  If unset, the launcher uses `llama-server` from `PATH`.
- The enhancer models and their system prompts are downloaded from the app's
  Settings → Models page (step 5); nothing else to fetch by hand.

The other rewriter is any OpenAI-compatible chat endpoint (for example another
llama-server or vLLM). It is offered whenever the system prompts are installed,
at `http://127.0.0.1:8079/v1/chat/completions` unless you set
`QWEN_REWRITE_ENDPOINT`; set `QWEN_REWRITE=0` if you have none.

### 4. Start

```bash
./start-web.sh
```

The console lists every address it listens on, then `generation enabled`.
Open `http://127.0.0.1:8765/` on the machine itself (model downloads are only
offered there).

| Variable | Default | Effect |
|---|---|---|
| `QWEN_WEB_PORT` | `8765` | Port. |
| `QWEN_LAN_HOST` | the default route's private IPv4, if any | Extra listen address; `""` for none. |
| `QWEN_TAILSCALE_HOST` | `tailscale ip -4`, if any | Extra listen address; `""` for none. |
| `QWEN_PE_LLAMA_SERVER` | `llama-server` on `PATH` | Path to llama.cpp's server, for the official enhancers. |
| `QWEN_PE` | `1` | `0` leaves the official enhancers out. |
| `QWEN_REWRITE_ENDPOINT` | `http://127.0.0.1:8079/v1/chat/completions` | OpenAI-compatible chat endpoint for rewrites. |
| `QWEN_REWRITE_MODEL` | `Qwen3.8` | Model name sent to that endpoint. |
| `QWEN_REWRITE` | `1` | `0` leaves the endpoint rewriter out. |
| `QWEN_ATTEST_UNBOUNDED_HOST` | `1` | Set `0` inside a container or cgroup with a RAM limit. |
| `QWEN_ENCODER_THREADS` | auto | CPU threads for the text encoder (1–64). |

Browsers on other machines can use this PC's hostname instead of its IP: the
first start writes `cache/web-settings.json` with the hostname, its `.local`
name and its Tailscale name.

### 5. Get the models and run a test

1. Open **Settings → Models**. Download the required base model (~33 GB).
   Optionally tick the Q8 transformer and the official enhancers.
2. Back on **Create**, generate a 1K image with the default settings
   (Quality, FP16). The first job loads the models (about a minute).
3. Then try a 2K preset (the 1K/2K tabs above the aspect tiles).

### Testing on a 32GB card

Nothing has been run on a 32GB V100 yet, so these results are the useful
ones to report:

- the output of the probe command in step 2;
- whether a 1K and a 2K job (FP16) succeed, and the timings shown under the
  image;
- 2K at FP16 with a long prompt (over 1,600 characters). On 16GB this runs out
  of memory above ~500 prompt tokens, so the page shows a warning; on 32GB it
  should fit, and the warning can be ignored;
- anything in the `./start-web.sh` console that looks like an error.

The CPU test suite (no GPU needed) also runs on any machine:
`PYTHON=.venv/bin/python PYTHONPATH=src bash run_cpu_tests.sh`.

## Tests

```bash
bash run_cpu_tests.sh            # full suite; any pytest args pass through
```

The suite runs fully offline with no GPU or weights. A guard denies network
access, blocks torch/diffusers/transformers imports and confines all writes to
a throwaway temp directory.

## Layout

```
src/qwen_engine/      engine core, CLI, encoder worker, job controller
src/qwen_engine/web/  HTTP server for the web workspace (static UI in web_static/)
src/qwen_engine/adapters/  the only place heavy ML libraries are imported
models/               pinned manifests (weights themselves are gitignored)
tools/                model fetcher and standalone verification checks
scripts/              environment setup, preset sync, browser checks, benchmarks
tests/                CPU-only test suite
docs/                 design contracts, measurements and review notes
```
